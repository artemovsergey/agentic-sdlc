# Неделя 2. Практика: контекст-пакет и feedback loop

## Предусловия

- Заполнена постановка задачи из недели 1.
- Есть доступ к CollegeLMS и его `AGENTS.md`.
- Прочитан `lecture.md` этой недели.
- Открыт `results.md` — в него пишутся результаты шагов.

## Шаги

1. **Worktree.** Создайте отдельный worktree CollegeLMS вне прод-каталога и работайте только в нём. Если работаете в BB, worktree обычно создаётся вместе с тредом; ручной вариант:

   ```bash
   git -C /home/user1/CollegeLMS worktree add /home/user1/CollegeLMS-w02 -b feat/week-02-practice
   cd /home/user1/CollegeLMS-w02
   ```

   Проверьте, что вы в отдельном каталоге, а не в `/home/user1/CollegeLMS`. Прод-каталог не трогаем: там работают контейнеры.

2. **Контекст-пакет.** Под постановку недели 1 соберите в `## Контекст-пакет`: 3–7 файлов, которые участвуют в изменении; спеку или user story; ограничения из `AGENTS.md`; команды проверки; неизвестности. Для каждого файла — одна строка, зачем он нужен. Если файлов больше семи, объясните, почему без них не обойтись.

3. **Первый прогон проверок.** Передайте агенту контекст-пакет и постановку. Все команды выполняются из корня worktree. Замените `{Name}` на реальный фильтр тестов, а не оставляйте шаблон:

   ```bash
   dotnet build CollegeLMS.slnx
   dotnet csharpier check .
   dotnet test CollegeLMS.slnx --filter FullyQualifiedName~{Name}
   (cd CollegeLMS.Next && npm run build)
   (cd CollegeLMS.Next && npm run check:design-system)
   ```

   Frontend-команды стоят в подоболочке `( … )`: так блок копируется целиком и вторая команда не пытается войти в `CollegeLMS.Next` из уже открытого каталога. Проверьте, что фильтр выбрал хотя бы один тест: ноль найденных тестов — это не зелёный прогон, а ложное зелёное. Полный прогон тестов не запускайте: он идёт в CI.

   **E2E — только на изолированном стенде.** По умолчанию Playwright в этой неделе не запускается: worktree изолирует файлы, но не сервер и не базу. `playwright.config.ts` использует `localhost:3000` и `reuseExistingServer`, поэтому спек может подключиться к общему стенду или проду и изменить данные. Если отдельного стенда нет, запишите в журнал `не запускался: нет изолированного стенда` — это допустимый результат. Запуск разрешён только при собственном `PLAYWRIGHT_BASE_URL` и одноразовой тестовой базе; мутирующие спеки (`POST`, `PUT`, `PATCH`, `DELETE`) против общего стенда запрещены.

4. **Исправление и повторный прогон.** Для каждой упавшей команды найдите первую ошибку и классифицируйте её: ошибка кода, ошибка проверки или проблема окружения. Исправьте причину и повторно запустите сначала упавшую команду, затем весь набор — до зелёного результата применимых проверок. Не переписывайте тест под результат, пока не поняли причину. Сверьте вывод с разобранным примером в `lecture.md`; расхождения запишите.

   Если ошибка существовала до вашего изменения или это проблема окружения, зафиксируйте её отдельно и оставьте навык 4 в статусе `в работе`: полностью освоенным он считается только после зелёного прогона.

5. **Журнал и пробелы `AGENTS.md`.** Заполните `## Журнал проверок`: для каждой команды — `cwd`, фактическая команда без плейсхолдеров, сколько тестов выбрано и выполнено, код возврата, первая ошибка с классификацией и путь к полному логу. Для неприменимой проверки напишите `N/A` и причину. Затем найдите 1–3 пробела: чего не хватило агенту, чтобы действовать без вопросов. Для каждого запишите формулировку, которую стоит добавить, и обоснование. Не коммитьте и не применяйте правки: это решение автора проекта.

6. **Самодиагностика.** Оцените навыки 3–4 по вопросам из `course/roadmap.md`. Обновите `roadmap.md` только при наличии доказательства: контекст-пакет, журнал проверок, ссылка на коммит или запись в `results.md`.

## Границы

- Только отдельный worktree, не прод-каталог `/home/user1/CollegeLMS`.
- Не трогать миграции, `.env`, `docker-compose.yml` и workflow.
- Не коммитить, не мержить и не пушить в CollegeLMS: изменения остаются в ветке worktree.
- Не запускать Playwright против общего стенда или прода: worktree не изолирует базу.
- Не применять правки `AGENTS.md` самостоятельно: только предложения в `results.md`.

## Критерий готовности

Практика завершена, когда:

- контекст-пакет объясняет, зачем нужен каждый файл;
- журнал проверок воспроизводим: у каждой команды есть `cwd`, фактическая команда, код возврата, число тестов и путь к логу;
- для каждой упавшей команды указана первая ошибка и её причина;
- после исправлений выполнен повторный прогон, применимые проверки зелёные, а `N/A` обоснованы;
- предложения по `AGENTS.md` конкретны и обоснованы;
- `results.md` заполнен, раздел `## Артефакт` содержит ссылки на журнал и предложения.
